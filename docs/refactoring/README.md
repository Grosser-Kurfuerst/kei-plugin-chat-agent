# 模块化重构方案

覆盖：现有实现的模块边界、职责整理、子包拆分、迁移顺序、规模预估与验收。不覆盖：新增会话概括、知识图谱、跨群成员记忆或用户画像，以及 kei 宿主功能开发。

本方案是重构实施依据。现有行为与运行时契约继续以项目各功能文档为准；实施时同步更新对应文档，交付状态统一记录在 [`roadmap.md §16.1`](../roadmap.md#161-现状)。本方案不占用项目正文的第 1–16 章编号。

## 目标与范围

采用“先收拢职责，再拆独立子包”的方式整理代码：先在根包内拆分混合职责，再将边界稳定的基础能力迁入本仓库的 `internal/` 子包。

重构保持插件注册方式、配置键、命令与输出、提示词、存储键及行 JSON 形状、检索与合并规则、任务互斥和关闭语义。现有功能缺口单独处理，避免与结构迁移混在同一批变更中。

根包仍为 `chatagent`，Go module 与宿主空导入路径保持稳定。运行时依赖继续限定为标准库与 kei 的公开插件 API。

## 模块边界

以 [`architecture.md §2.4`](../architecture.md#24-组件职责) 和 [`§5`](../architecture.md#5-目录与文件职责) 为基础，按以下八个职责组织实现。职责模块不要求各自对应一个 Go 包。

| 模块 | 职责 | 现有入口与整理方向 |
|---|---|---|
| 插件装配与配置 | 注册、配置读取、组件初始化、启动与关闭 | [`register.go`](../../register.go)、[`plugin.go`](../../plugin.go)、[`config.go`](../../config.go)；配置按定义与默认值、读取、校验拆文件 |
| 消息参与与回复 | 准入、寻址、随机参与、批处理、生成和发送 | [`decision.go`](../../decision.go)；拆分消息决策、批处理与回复生成 |
| 会话与上下文 | 会话状态、历史、快照、上下文渲染与清理 | [`state.go`](../../state.go)、[`history.go`](../../history.go)、[`prompt.go`](../../prompt.go)；收回调度器中的历史清理逻辑 |
| 长期记忆 | 抽取、整理水位、合并、强化、衰减与管理操作 | [`memory.go`](../../memory.go)；按抽取、整理、写入治理、生命周期拆文件 |
| 知识库 | URL／文本导入、正文提取、分块、更新与删除 | [`knowledge.go`](../../knowledge.go)；分离网络抓取、文档处理与导入流程 |
| 检索与上下文注入 | 查询构造、双库召回、阈值过滤、预算与注入块 | [`rag.go`](../../rag.go)；保留为在线回复的检索编排入口 |
| 基础能力 | 模型请求、安全下载、串行持久化、索引与向量计算 | [`llm.go`](../../llm.go)、[`embedding.go`](../../embedding.go)、[`vision.go`](../../vision.go)、[`storage.go`](../../storage.go)、[`vector.go`](../../vector.go)；分批迁入独立子包 |
| 管理与任务调度 | 授权、命令解析、任务触发、互斥、状态与结果回复 | [`admin.go`](../../admin.go)、[`commands.go`](../../commands.go)、[`scheduler.go`](../../scheduler.go)；命令调用业务操作，调度器负责运行控制 |

## 第一阶段：根包内整理职责

本阶段保持 `package chatagent`，优先移动完整函数与相关类型，保留函数签名、锁边界及调用顺序。以下文件名为迁移目标；实际文件职责表在迁移时更新至架构文档。

| 调整对象 | 拆分目标 | 边界要求 |
|---|---|---|
| `decision.go` | `message.go`、`batch.go`、`reply.go` | 消息入口负责准入与参与决策；批处理负责 timer、pending 和触发；回复流程负责检索、模型调用、清洗与发送 |
| `scheduler.go` | 保留调度器；新增 `session_cleanup.go`、`vector_reindex.go` | `runCleanup` 回到会话模块，`runReindex` 与相关更新流程回到向量模块；互斥规则保留在统一调度入口 |
| `commands.go` | 保留授权与分发；按 `commands_memory.go`、`commands_knowledge.go` 等拆分 | 参数检查、固定输出与异步结果回复属于命令层；记忆增删、搜索、重置等业务操作归对应模块 |
| `memory.go` | `memory_extract.go`、`memory_consolidate.go`、`memory_store.go`、`memory_lifecycle.go` | 抽取与校验、批次及水位、合并与写入、强化及淘汰分别归位 |
| `knowledge.go` | `knowledge_fetch.go`、`knowledge_text.go`、`knowledge.go` | 抓取、正文提取及分块、文档导入与更新分别归位 |
| `vector.go` | `vector_record.go`、`vector_load.go`、`vector_search.go`、`vector.go` | 行形状与编码、启动加载、top-k、索引状态及原子更新分别归位 |
| `storage.go` | 保留单写队列与持久化入口 | 向量编码归向量模块；文本清洗与截断归实际使用模块，避免形成杂项工具集合 |
| `config.go` | `config.go`、`config_parse.go`、`config_validate.go` | 配置键与默认值语义保持一致，公开配置仍以配置文档为唯一权威 |

测试随职责移动，优先保留现有用例与断言。端到端测试、跨模块竞态和关闭测试继续验证整体链路。

## 第二阶段：抽取基础子包

根包保留宿主接入、业务流程与统一生命周期；先形成四个基础子包：

```text
仓库根目录（package chatagent）
├── register.go / plugin.go       插件入口、装配与生命周期
├── config*.go                   配置读取与校验
├── message.go / batch.go         消息参与与批处理
├── reply.go / prompt.go          回复编排与上下文组装
├── session*.go / history.go      会话与历史
├── memory*.go                   长期记忆业务
├── knowledge*.go                知识库业务
├── rag.go                       检索与注入编排
├── commands*.go / admin.go       命令与授权
├── scheduler.go                 调度与任务互斥
└── internal/
    ├── modelclient/             Chat、Embedding、HTTP 错误与重试
    ├── webfetch/                安全下载、地址检查与图片校验
    ├── storage/                 KV／表行单写队列
    └── vector/                  记录、编码、加载与内存索引
```

依赖与所有权约束：

- 根包调用子包；子包不反向导入根包，不接收整个 `*Plugin`。配置由根包读取，按组件需要传入具体参数，子包不自行读取环境变量或本地文件。
- `modelclient` 接收宿主提供的 HTTP client、模型参数与日志器，保留现有 Chat／Embedding 注入能力；已有导出请求、响应类型的引用兼容通过根包类型别名维持。
- `webfetch` 管理受限 HTTP client、地址检查与下载；图片和知识库分别传入自己的访问、大小、格式与重定向规则，保持现有行为差异。
- `storage` 管理统一写队列的准入、执行、结果等待与排空；记忆水位推进、知识库提交点由业务流程决定。
- `vector` 统一持有索引记录、锁、版本校验与索引状态，通过方法提供快照和更新；业务不直接访问内部 map，也不把原来的原子操作拆成无保护的多次调用。
- 向量模块加载流程使用存储模块提供的写入能力；存储模块不依赖向量记录类型，避免循环依赖。表初始化与全量读取仍由 `Start` 阶段发起。
- 子包工作协程仍纳入插件实例的 `WaitGroup` 和插件级 context。关闭顺序继续遵循 [`architecture.md §3.4`](../architecture.md#34-关闭顺序)，统一关闭写入准入并排空队列，再取消后台工作。

接口只保留调用方需要的操作及现有测试注入点；普通组件优先使用具体类型。业务模块继续在根包编排，不为每个文件增加接口或服务层。

## 迁移顺序与规模预估

规模为规划估计，按每批实际差异复核；移动行数不等于新增逻辑量。

| 批次 | 工作内容 | 规模与验收重点 |
|---|---|---|
| 基线检查 | 核对 `go.mod` 的本地 `../kei` 替换、公开表存储接口与开发工具链；运行现有质量门 | 若有依赖或环境阻塞，先记录并单独解决，再建立重构前测试基线 |
| 根包职责整理 | 完成第一阶段拆分，同步函数归属、测试位置与文档 | 小到中等；预计涉及约 10–15 个现有生产文件及对应测试，以移动为主；检查调用顺序与行为保持 |
| 模型与下载子包 | 依次迁移 `modelclient`、`webfetch`，每个子包单独验收 | 中等；重点验证请求协议、错误分类、重试、多模态输入、SSRF 与下载限制 |
| 存储子包 | 迁移统一写队列，根包保留生命周期装配 | 中等；重点验证写失败、任务取消、关闭准入与排空 |
| 向量子包 | 迁移记录、编码、加载、查询与状态更新，调整业务调用 | 中等且影响范围最大；重点验证快照、版本校验、容量、文档提交、reindex 与并发删除 |

整体按中等规模重构安排，逐批完成；第二阶段会影响多数生产文件的调用点与部分测试。第一阶段可以独立交付，每个子包迁移也应保持可构建、可测试。

依赖状态需要在实施时重新核对。先前接口缺失或测试失败的观察不能代替当前基线，也不能直接作为修改 kei 宿主的依据。

## 文档与验收

实施时按变更涉及的职责同步文档：

- [`architecture.md §2.4`](../architecture.md#24-组件职责)、[`§3`](../architecture.md#3-生命周期与并发模型) 与 [`§5`](../architecture.md#5-目录与文件职责)：同步组件边界、资源所有权和实际文件布局。
- [`testing.md §15.2`](../testing.md#152-单元测试矩阵) 与 [`§15.3`](../testing.md#153-测试注入缝)：同步测试归属与注入方式。
- 各功能文档中的源码类型或文件引用随迁移更新；配置键、命令文案和存储形状继续引用原权威章节。
- 完成情况只更新 [`roadmap.md §16.1`](../roadmap.md#161-现状)，本方案不维护第二份进度清单。

每批代码变更在 flake devShell 中执行 [`testing.md §15.1`](../testing.md#151-质量门) 的完整质量门。重点复用现有用例验证以下契约：

- 名单与准入顺序、同一会话批处理串行、全局生成并发限制。
- 历史裁剪与整理水位、写入失败后的重试、记忆合并及衰减。
- 知识库文档提交顺序、索引更新与重建、双库预算及提示词注入。
- 图片下载限制、失败占位与多模态内容组装。
- 管理员授权、命令同步／异步输出、任务互斥。
- `Stop` 的准入关闭、写队列排空、取消及等待；竞态测试与 mock 宿主端到端场景。

文档变更检查相对链接、索引、锚点及全局章号。只有行为、接口或状态所有权发生调整时补充必要测试，纯函数移动不新增镜像实现的测试。
